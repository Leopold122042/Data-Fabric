# 自然语言查询：意图到操作

用户工作台 `/api/portal/queries` 使用 `semantic_query.prepare`，不再调用旧的
“姓名的字段”正则规划路径。管理页的历史流程保留兼容，新计划不允许历史修复器重写。

1. 只向本机 Ollama 发送用户需求、目录字段含义、明确的字段引用、已确认患者关系与当前日期。
2. 模型输出结构化对象：查询对象、输出、比较条件、排序、条数、记录选择操作（普通/最近/最早）、理解摘要、必要问题。
3. 编译器从当前目录绑定字段，通过 SQL AST 构造查询。模型不直接生成可执行 SQL。
4. 复用统一只读查询校验器，检查字段定义、交付分类、已确认关系和操作支持范围。
5. 展示模型摘要和**由实际计划生成的条件、输出、条数**。人工确认后建立不可变规格和方案。
6. 原有访问审批、授权、执行和交付检查继续生效；生成意图不读取源数据。

## 当前支持范围

- 明细查询，1–10 个输出字段，最多两张具有已确认患者关联的表。
- 1–20 个同时成立的比较条件：`= != < <= > >=`，参数化执行。
- 日期字段条件独立于执行期限；不再禁止出生日期比较。
- 多字段排序与 1–200 条限制。不足请求条数时返回实际记录。
- 未指定患者列表输出时，模型建议患者编号和筛选字段，在确认界面明确展示。
- 需要补充信息时保留原需求与回答，在同一需求和流程中重新规划。

OR、聚合、任意多表组合、无法确认的关联等尚未实现的操作应提出具体问题，不能丢弃条件执行近似查询。
编译器及确认入口校验“最近/最早”的排序字段必须属于查询记录自身且具有时间语义，方向必须一致。
文书没有时间时不能用患者编号、文本或另一张表的时间冒充“最近”。已有确认关系直接提供给模型，不重复询问用户。
模型格式错误先重试；持续结构错误提示模型解析失败，不让用户去补不存在的字段。

## 验证

`tests/integration/test_semantic_query.py` 覆盖完整受控交付、出生日期边界、AND 条件、数值比较、排序、
条数、澄清后条件保留、未知字段、非法操作、反向比较与注入字符串。
`tests/execution/test_constraints.py` 的日期窗口样本按现有北京时间日界规则校正，
包含当地一月最后一秒、排除当地二月零点；没有更改产品的时区规则。

本机模型实测与模拟模型单元测试分别进行；真实模型结果不等于任意自然语言均已覆盖。
