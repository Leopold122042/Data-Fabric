====================================================================
一、总体架构一句话
====================================================================
MedFabric 模拟三甲医院的 HIS / LIS / PACS / EMR / IoT 五套异构数据源，它们物理分散存放；平台不搬迁任何一条物理数据，而是在「元数据」之上持续感知各源状态，建立语义映射与逻辑视图，对外提供联邦查询、智能编排、服务流通与安全治理能力。

三层架构（对应申报书第一部分的分层模型）：
  资源层   五套模拟的医院侧数据源（物理分散，各自独立存储）
        |
          编织层   主动元数据发现 -> 统一语义建模/知识图谱 -> 数据虚拟化(逻辑视图)
                |
                  服务层   数据服务目录与流通 + 智能编排调度 + 安全合规治理
                  
五套模拟源（见 medsim.py 的 SOURCE_DEFS）：
  his    HIS医院信息系统        Oracle 19c 模拟(SQLite文件 his.db)     患者主索引/就诊/医嘱，位于「院内数据中心」
    lis    LIS检验信息系统        MySQL 8.0 模拟(lis.db)                 标本采集、检验申请单与结果明细
      pacs   PACS影像归档系统       PostgreSQL+DICOM文件库模拟(pacs.db)     CT/MR/DR/US检查索引，文件保持原位存于影像服务器
        emr    EMR电子病历            MongoDB文档库模拟(emr/*.json)          半结构化病程记录与诊疗文书，每患者一个JSON文件
          iot    IoT院内监测设备网      Kafka+InfluxDB流模拟(iot.db)           床旁监护仪连续生命体征流
          
基准数据用固定随机种子生成（可复现）：180名患者、490余次就诊、数千条检验结果项；其上 StreamingSim 持续注入「新患者」实时业务流这正是主动元数据发现演示「边跑边发现」的素材。

====================================================================
二、核心概念：什么是「主动元数据」
====================================================================
传统（被动）的目录方式：人工登记一次表和字段，之后除非有人记得去改，目录就一直是旧的在真实医院环境里它几乎必然过期。

主动元数据 = 持续感知 + 自动触发动作：
系统自己周期性重扫各源，与「上次看到的样子」比对；一旦有差异（新表、新列、行数增长、数值越界、同一患者出现在多个系统中），立刻生成结构化事件；事件同时驱动下游动作目录更新、图谱重建、告警下发、任务入队。没有人参与，闭环自动完成。

在本平台中的落点：
- 「感知」由 discovery.py 承担（DiscoveryEngine + SourceAdapter + EventBus）；
- 扫描周期 SCAN_INTERVAL = 4.0 秒（app.py），每 4 秒全量扫一轮五源；
- 事件按发生顺序编号 seq，EventBus 保留最近 800 条，通过 SSE（/api/stream）实时推送给前端 UI。

====================================================================
三、发现是怎么做的：逐步机制（discovery.py）
====================================================================
第1步 统一适配器 SourceAdapter
每类源实现统一的 snapshot() 接口，回答「这个源现在长什么样」：
- 关系型源(HIS/LIS/PACS/IoT)：读 sqlite_master 拿表名；对每张表用 PRAGMA table_info 取列清单、COUNT(*) 取行数；结构指纹 hash = md5(「表名|列1,列2,...」)的前16位中的前12个十六进制字符。
- 文档型源 EMR：抽样最近40个JSON文件，把顶层键集合当作「文档模式」的虚拟列清单，行数=文件数，指纹同样按 md5(键集) 计算。

第2步 差异比对 scan_source()
每次扫描取当前快照与内存中上一轮快照(last[sid])对比：
- prev 为空 => 该源首次纳管 -> catalog_built 事件（「首次纳管，元数据目录已建立」，detail列出各表行数）；
- 出现新表   => schema_change 事件（检测到新逻辑表，附列结构）；
- 指纹变化且无新增列 => 「字段定义/统计特征变化」；若有新增列 => detail直接点名「新增列：xxx,yyy」；
- 仅行数增长  => data_update 事件，并由 summarize() 生成人类可读摘要（见下例）。

第3步 内容级检查（不只是结构）
IoT 源每次扫描额外做值域体检：回读 vitals 最近40个监测点逐条判断 heart_rate>=125 或 spo2<=93.5，命中即发 quality_anomaly 事件；用「患者ID:分钟级时间戳」作冷却键去重同一患者同一分钟内持续越界只报一次（防止监护流造成事件风暴）。

第4步 跨系统身份对齐 _identity_pass()
每轮扫描末尾还会回答「谁在哪些源里出现过」：对 his/lis/pacs/iot 各做 SELECT DISTINCT patient_id，EMR 用文件名即患者ID；某个 pid 首次同时出现在 >=2 个源中 => semantic_link_discovered 事件（「完成跨系统身份对齐」，detail列出全部来源与数量）。这就是把互不信任的系统里的「同一个人」自动缝合起来的机制。

第5步 事件分发
所有事件进入线程安全的 EventBus（seq单调递增），同时喂给两条下游：
- UI 实时面板 / SSE 推送（人看）；
- orchestration.py 的 handle_events() 规则匹配 -> 自动生成任务进优先级队列（机器执行，见第七部分）。

四、具体例子（以下全部可在本平台真实复现）
====================================================================
【例1】一个新患者的完整旅程：看主动元数据把五套系统里的同一个人实时缝合出来
背景：StreamingSim 大约每4秒注入一名新患者，并分阶段、每隔约8/12/16秒依次落库（模拟真实业务节奏：先监护、后建档）。

T+0s     阶段0：只写入 iot.db  3个生命体征点（心率随机落在96~138之间）。
         此刻 HIS/LIS/PACS/EMR 里完全没有这个人的任何记录。
         T+4s     发现引擎本轮扫描：iot.vitals 行数增加 -> data_update 事件「IOT.vitals +N行」；
                  若心率恰好 >=125，同时发出 quality_anomaly（后续链条见例6）。
                  T+8~16s  阶段1：his.db 写入 patient 主档与 visit 就诊登记。
                           下一轮扫描产生 data_update 事件，summarize() 输出人类可读摘要：
                                      「P0185 张伟 新建档」（取 HIS.patient 最新一行）
                                                 「新增就诊 P0185  心内科（原发性高血压）」（取 HIS.visit 最新一条）
                                                 T+下一轮 阶段2：lis.db 写入检验申请单 test_order + result 明细6项。
                                                          （数值按参考区间的0.85倍~1.12倍随机分布，超出上限标H、低于下限标L。）
                                                                   -> data_update「LIS.result 增量N行」；同时 R-LIS 规则扫描该患者最近一张检验单的异常项（见例7）。
                                                                   T+下一轮 阶段3：pacs.db 以0.7概率写入一条影像 study，且同一步把 EMR 文书 P0185.json 落盘。
                                                                            -> data_update「新增 CT 影像检查：P0185/胸部」；EMR 文件数 +1（见例3的文档模式指纹）。
                                                                            T+4s     身份对齐回合发现 P0185 首次出现在 >=2 个源中（实际走到这一步通常已覆盖3~5个源）->
                                                                                     semantic_link_discovered：「张伟(P0185)完成跨系统身份对齐」，detail列出全部来源名与数量。
                                                                                     
结果：在 UI「主动元数据发现」页的事件流里，你能亲眼看到四秒前还不存在的人，被逐步缝合进知识图谱没有写任何一行ETL程序，也没有搬迁一个字节的数据。


【例2】Schema 漂移（结构变更）
假设 LIS 侧有人给 result 表加了一列「审核人」，或者干脆新建了一张表：
- 下一轮扫描发现该表的 md5 指纹变化 -> schema_change 事件（severity=warn）；
- detail 自动点名新增的列（「新增列：reviewer」）并附当前行数；若是全新表格则报「检测到新逻辑表 xxx，列结构：...」；
- 联动效果：元数据目录(GET /api/catalog)立即带上新结构刷新展示；R-SCHEMA规则(P1优先级)被触发执行「语义重映射校验」重新统计各源逻辑表/总列数，对照 semantics.FIELD_MAP 的33条字段级映射计算覆盖率，提示哪些新列还缺语义登记。
要点：指纹只由「表名+列清单」算出，所以纯数据行增长不会触发结构事件；而任何加列、删列、新建表都会在4秒内被发现并自动进入目录与校验流程。


【例3】文档型源（EMR）的发现：没有表怎么比对？
EMR 没有关系表，是每患者一个 JSON 文件。EmrAdapter 用「文档模式指纹」处理：抽样最近40个文件，把它们的顶层键集合当作虚拟列清单chief_complaint / present_illness_history / physical_exam / auxiliary_examination / preliminary_diagnosis / treatment_plan ...
- 新患者的 Pxxxx.json 出现 => 行数(=文件数)+1 -> data_update；summarize() 输出「N份病历文书（最新 xxx 落档）」；
- 若某类文书新增了字段（例如 discharge_summary）且进入抽样窗口 => 键集合变化、指纹漂移 => schema_change。
这正是主动元数据对半结构化/非结构化数据的推广方式：不逐条读内容，先建立结构与模式的统计画像再比对。


【例4】单源故障容错（纳管不等于绑死）
若某个源扫描时抛异常（例如文件被占用、库损坏）：该源的 last_scan 标记为「12:03:05(失败)」，其余四源照常扫描；并且只在首次失败时发一条带 detail 的「扫描异常」事件，后续重复故障不再刷屏。这体现数据编织多源纳管中的故障隔离原则一个源出问题不拖垮整体感知链路。


【例5】手动触发与增量回放（复现任意事件的技巧）
- POST /api/discovery/run {"source_id":"lis"} 可立即重扫单个源；不带参数则全量扫描（UI发现页有「手动扫描」按钮）。
- GET /api/events?after=1234 按 seq 增量取事件；GET /api/stream 是 SSE 长连接，前端直接订阅实时流。
复现方法：用 sqlite3 工具往 lis.db 的 result 表手工插一行（或加一列），再点一次手动扫描最多等一个扫描周期(4秒)，对应 schema_change / data_update 事件就会出现在 UI 上。


【例6】质量异常 -> P0任务全链路：感知-建模-执行-反馈闭环
触发条件：iot.vitals 最近40个监测点中任一点满足 heart_rate>=125 或 spo2<=93.5。
完整血缘（每一环都能在 UI「智能编排调度」页的任务流里看到）：
  1 感知   扫描发现 P0187 最新点 HR=131、SpO2=92.6 -> quality_anomaly 事件(编号 seq=N)，
             detail：「心率131 bpm、血氧92.6%已触发告警并建议核查监护设备与临床状态」；
               2 建模   handle_events() 按 etype 匹配规则，只有 R-QA（体征异常复核）命中该事件类型；
                 3 调度   任务以 P0(最高优先级)进入队列，串行 worker 取出执行（P0>P1>P2，避免并发写冲突）；
                   4 执行   _act_qa：回读该患者最近12个体征点复核极值，并调用 SVC-VITALS-TREND 服务生成告警趋势包（记录服务往返时延）；
                              任务结果文本形如「P0187 复核：HR峰值138.4 / SpO2谷值92.1%，越界属实；告警趋势包已生成(服务往返xx ms)」；
                                5 反馈   动作完成后回写一条 orchestrated_action 事件进元数据流（驾驶舱「闭环」条带计数+1）；
                                           防自激设计：handle_events() 明确跳过这种反馈类事件，不再触发新任务否则告警调服务、服务调用又产生事件，会无限循环。
                                           

【例7】LIS检验结果增量 -> 异常项扫描（P2级规则演示三级条件过滤）
命中条件是三级的组合：etype=data_update AND source_id=lis AND title包含「LIS.result」。
动作 _act_lis：定位最新回报患者的最近一张检验单，按参考区间统计 H/L 标志项，输出形如「T103845 P0092 最近检验6项，异常(H/L)2项：谷丙转氨酶、白细胞计数」。
这条规则的意义在于展示编排条件不只是单一事件类型，还可以叠加源ID与标题关键词做精确过滤。

五、语义建模与知识图谱原理（semantics.py）
====================================================================
1 实体体系 ENTITY_TYPES：六类patient患者 / visit就诊 / lab_test检验单 / imaging_study影像检查 / vitals_series生命体征流 / emr_doc病历文书，各带标签与描述。

2 字段级跨源映射 FIELD_MAP：共33条，形式为 (source.table.column -> entity.attribute)，例如：
   his.patient.id_card       -> patient.证件号(敏感)
      lis.result.value_num      -> lab_test.检验值
         pacs.study.modality       -> imaging_study.模态(CT/MR/DR/US)
            iot.vitals.heart_rate     -> vitals_series.心率(bpm)
            关键点：物理表一律不动，只在语义层建立映射这是「逻辑关联整合」与「物理集中汇聚」的本质区别。
            
3 术语对齐 TERMINOLOGY：ICD-10诊断代码表 + LIS检验项目参考区间表（medsim.DIAGNOSES / LAB_ITEMS）。tag_diagnoses() 对就诊的诊断码逐条打上标准名称、科室提示与 aligned 标志；未登记的编码会如实标为「未收录诊断(aligned=False)」而不是静默丢弃元数据要诚实。

4 知识图谱 build_graph()：取按最近就诊时间排序的40名患者为核心节点向外展开患者->就诊/检验单/影像/体征监护/病历文书，每条边带置信度 conf：
   就诊关联 0.99、检验申请 0.97、影像关联 0.96、病案归档 0.95、生命体征监护 0.93。
      规律：系统间显式外键约束越强，置信度越高；IoT流没有正式建档关系（只凭patient_id字符串匹配），所以最低。这正是知识图谱「带置信度的边」的典型用法下游可据此决定是否采信某条关联。
      

====================================================================
六、数据虚拟化与零拷贝联邦查询（virtualization.py）
====================================================================
1 逻辑视图目录：直接从 FIELD_MAP 按实体分组推导而来例如 patient 的逻辑视图横跨 his.patient、lis.test_order(patient_id)、pacs.study(patient_id) 等物理表；每条视图列出涉及源清单 physical_tables。视图是元数据的「派生物」，不是人工建出来的中间表。

2 Patient360（POST /api/query/patient_360 {"patient_id":"P0185"}）：对给定患者ID依次联邦读取五源基本信息 -> 就诊与医嘱 -> 检验结果(含H/L异常项计数) -> 影像检查索引 -> 生命体征趋势(附均值/峰值统计) -> 病历文书。
   - 每个分节记录自己的 latency_ms，外加 total_latency_ms 总耗时；响应带 zero_copy=true，表明全程没有迁移任何数据；
      - 基本信息的 id_card 在接口层已脱敏输出为 id_card_masked（敏感字段不明文出源）；
         - 附 semantic_tags：对该患者最近6次就诊的诊断码做 ICD-10 批量术语对齐。
         
3 与传统集成方式对比：物理集中要建数据仓库、T+1同步，且一旦落仓就产生第二份数据的维护与合规负担；虚拟化方案里 PACS 的 DICOM 文件始终留在影像服务器（只读索引）、EMR 文书从病案库按需读取、IoT 流由边缘网关直读「数据保持原位，访问按需发生」，这正是申报书第二部分强调的逻辑集成路线。

七、智能编排调度原理（orchestration.py）
====================================================================
内置5条规则 RULES_DEF：
  R-QA      P0   体征异常复核与告警下发     触发条件: quality_anomaly
    R-LINK    P1   身份对齐语义登记           触发条件: semantic_link_discovered（动作:刷新图谱节点与逻辑视图实例）
      R-SCHEMA  P1   语义重映射校验             触发条件: schema_change（动作:重新计算字段级跨源映射覆盖率）
        R-LIS     P2   检验异常项扫描             触发条件: data_update AND source=lis AND title含LIS.result
          R-PATROL  P2   全源质量巡检(定时调度)      无事件触发：每180秒自动执行一次，也可手动 POST /api/orchestrator/patrol
          
调度机制要点：
- 优先级队列 P0>P1>P2；串行受控执行（worker线程逐个跑，避免并发写同一资源）；
- 任务血缘链完整可追：触发事件 seq -> 任务 tid -> 结果/反馈事件，UI任务流逐条展示；
- 每条规则独立统计命中数、完成数、平均时延(ms)，支持在线启停（POST /api/rules/{id}/toggle）。

两类调度的互补关系：事件驱动编排负责「发生了就立刻处理」（实时性），周期巡检 R-PATROL 负责「定期体检」每180秒核对五源行数快照与事件积压，校验血缘链完整性并输出巡检摘要。两者合起来构成完整的自动化调度能力（感知-建模-执行-反馈闭环的「执行」环节）。

八、安全合规治理原理（governance.py，简述）
====================================================================
1 分级分类：六类医疗数据资产按敏感度分 L1~L4；GOVERNANCE 集中登记各源级别与脱敏策略HIS核心业务数据(证件/手机号脱敏存储,查询留痕)、LIS临床敏感(检验值按科室权限分级可见)、PACS大对象影像资产(DICOM文件保持原位仅索引出域,报告字段级授权)、EMR临床敏感(文书读取即脱敏,id_card/phone不落接口)、IoT近实时监测流(边缘网关直读,原始波形不出院区)。

2 细粒度动态授权：四类角色策略（临床医生/数据分析师/科研人员/运维）；每次访问请求按「角色 x 资产分级 x 用途 x 是否跨组织」四个维度实时评估，返回三种决策之一allow / allow_masked(脱敏后放行) / deny。POST /api/security/authorize 可在线演示任意组合的判定结果。

3 全链路审计：每次授权决策、服务调用、流通阶段都生成带编号的审计记录（主体+组织+操作+时间+决策+理由+策略链），GET /api/security/audit 查询满足「谁在何时以什么身份对哪份数据做了什么」的可追溯要求。

4 风险预警与处置：越权访问、用途不符、跨域未授权会自动生成风险工单；UI支持人工复核后关闭（POST /api/security/risks/{rid}/resolve），形成「发现-告警-处置-销号」的闭环。
